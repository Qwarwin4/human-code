# Заметки по языкам

Открывай только нужный раздел. Общее правило везде одно: стиль существующего проекта главнее.

## Содержание
- Python
- Go
- Rust
- C / C++
- C#
- JavaScript / TypeScript
- Dart / Flutter
- Kotlin / Java
- Bash / shell

## Python

- Типы в сигнатурах — ок, на локальных переменных — нет. `from typing import List, Dict` в 3.9+ не нужен: `list[str]`, `dict[str, int]`, `X | None`.
- `pathlib` вместо `os.path` в новом коде; `with open(...)` без лишнего `try`.
- f-строки, comprehensions, `enumerate`, `zip`, распаковка. `any()`/`all()` вместо флагов в цикле.
- `if not items:` вместо `if len(items) == 0:`; `return cond` вместо `return True if cond else False`.
- `dataclass` — когда у объекта реально есть поля и он передаётся; не для трёх настроек скрипта.
- `if __name__ == "__main__":` — да в модулях, которые импортируются; в одноразовом скрипте можно без.
- `logging` — в сервисах и библиотеках; в скрипте `print` нормален. `sys.exit("bad args")` — нормальный способ упасть с сообщением.
- Ловить конкретные исключения: `except FileNotFoundError`, `except KeyError`. Голый `except Exception: pass` — только с причиной.

## Go

- Короткие имена — норма языка: `r`, `w`, `ctx`, `err`, `n`, `buf`, `c` для клиента, получатель метода — одна-две буквы (`func (s *Server)`).
- `if err != nil { return fmt.Errorf("read cfg: %w", err) }` — оборачивай с коротким контекстом строчными буквами, без «failed to» в каждом слое.
- Не создавай интерфейс, пока нет второй реализации или теста, которому он нужен. Интерфейсы объявляет потребитель.
- Нет геттеров `GetName()` — просто `Name()`.
- Комментарии к экспортируемым сущностям приняты (`// Run starts ...`), но короткие, одной строкой. На неэкспортируемом — только если нужно.
- `gofmt`. Без выравнивания и пустых строк ради «секций».
- `log.Fatal` в `main` — норм; `panic` — не для обычных ошибок.

## Rust

- `?` везде, где можно; `anyhow`/`thiserror` по проекту. `unwrap()` — допустим в тестах, прототипах и там, где инвариант очевиден (тогда лучше `expect("...")` с короткой причиной).
- Не клонируй ради удобства, если можно занять ссылку; но и не воюй с borrow checker ценой нечитаемости.
- `impl Trait` в аргументах, итераторы с `map/filter/collect` вместо ручных циклов, где это проще читается.
- `match` с ранним возвратом; `if let`/`let else` вместо вложенности.
- Док-комменты `///` — на публичном API крейта; внутри бинарника — по необходимости.
- `rustfmt`, `clippy` без лишних `#[allow]`.

## C / C++

- Стиль именования и скобок — строго как в проекте (snake_case, camelCase, Allman/K&R).
- C++: `auto`, range-for, `std::unique_ptr`, `std::string_view`, `std::optional`. Без `new`/`delete` вручную в новом коде.
- Не пиши класс-обёртку `XManager` над тремя функциями — свободные функции в namespace нормальны.
- Doxygen `@brief @param @return` — только если проект им пользуется.
- В C: короткие имена (`fd`, `len`, `p`, `buf`), `goto out;` для очистки ресурсов — нормальная человеческая идиома.
- Не добавляй `#pragma region`, баннеры лицензий и шапки «File: foo.cpp / Author / Description», если их нет в соседних файлах.

## C#

- `var` для локальных, где тип очевиден справа. Expression-bodied members для однострочников.
- `?.`, `??`, `is not null`, pattern matching, `using var`.
- XML-доки `/// <summary>` — на публичном API библиотеки; в приложении на приватных методах не нужны.
- Не плоди `IFooService` + `FooService` на каждую сущность, если нет DI-контейнера и второй реализации.
- `async`/`await` без `.ConfigureAwait(false)` в приложениях (в библиотеках — по проекту).

## JavaScript / TypeScript

- `const` по умолчанию, `let` когда переприсваивается. Стрелочные функции, деструктуризация, `?.`, `??`, шаблонные строки.
- TS: не аннотируй то, что выводится (`const n: number = 5`). Типы — на границах (параметры, экспорт, ответы API).
- Не оборачивай каждый `fetch` в `try/catch` с `console.error` и `return null` — пусть ошибка всплывёт туда, где её покажут пользователю.
- `console.log` не оставлять, кроме намеренного вывода в CLI.
- Ванильный JS — без лишних классов; модуль с функциями нормален.
- JSDoc — только если проект без TS и его использует.

## Dart / Flutter

- `final` по умолчанию, `const` конструкторы виджетов, где можно.
- Не дроби `build` на десяток `_buildXxx()` по пять строк — либо оставь в дереве, либо вынеси в отдельный виджет, если он переиспользуется или реально большой.
- `?.`, `??`, `!` — по месту; `late` — только если действительно инициализируется позже.
- `dart format`. Без комментариев над каждым виджетом в дереве (`// Title text`).

## Kotlin / Java

- Kotlin: `val`, data class, extension-функции, `?.let`, `when`, scope-функции без вложенности в три уровня.
- Java: `var` (10+), records, стримы — где читаются проще цикла. Без геттеров/сеттеров на всё, если это не бин.
- Javadoc на каждом приватном методе — нет.

## Bash / shell

- `set -euo pipefail` в начале — да, это обычная практика.
- Короткие имена переменных строчными: `dir`, `f`, `out`. Капслок — для экспортируемых env.
- Не печатай `echo "Starting script..."` и цветные баннеры без надобности.
- `[[ ]]`, `$(...)`, кавычки вокруг переменных. Функции — когда реально повторяется.
- Сообщение об ошибке в stderr и выход: `echo "no such dir: $dir" >&2; exit 1`.
