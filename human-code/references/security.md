## 1. Как искать дыры, которых нет в списках

Типовые уязвимости ИИ знает и так. Опасное — то, что вытекает из логики
конкретной программы: кто что может сделать, в каком порядке, с какими
правами. Это не вспоминается по шаблону, это выводится.

**Нарисуй в голове границы доверия.** Кто пользователи программы, кто может
быть атакующим (аноним, обычный пользователь, другой пользователь, админ,
другой процесс на машине, владелец сервера, с которым ты говоришь). Что каждый
из них контролирует. Данные, пересекающие границу, считаются враждебными до
проверки — даже если «их же присылает наш клиент».

**Выпиши инварианты.** Что должно быть правдой всегда: «пользователь видит
только свои заказы», «баланс не уходит в минус», «товар не продаётся дважды»,
«файл пишется только внутри data_dir», «команда от бота выполняется только
для владельца». Потом для каждого инварианта ищи путь, которым его можно
нарушить: другой эндпоинт, повтор запроса, параллельный запрос, другой
формат входа, прямой вызов в обход UI, старая версия клиента.

**Задай враждебные вопросы каждому входу:**
- слишком большой, пустой, нулевой, отрицательный, дробный, NaN, бесконечность;
- не тот тип (строка вместо числа, массив вместо объекта, дубль ключа);
- нулевой байт, перевод строки, управляющие символы, юникод-двойники,
  другая нормализация, другой регистр, пробелы по краям;
- ссылается на чужой объект (чужой id, чужой путь, чужой chat_id);
- пришёл дважды, пришёл одновременно с другим, пришёл не по порядку,
  пришёл после того, как права отозвали;
- пришёл не оттуда, откуда должен (поддельный вебхук, локальный процесс,
  другой origin).

**Задай вопросы каждому состоянию:** что, если между проверкой и
использованием оно поменялось; что, если процесс упадёт посередине; что
остаётся после ошибки — полузаписанный файл, списанные деньги без заказа,
выданный предмет без оплаты.

**Посмотри на отказ.** Если проверка подписи, авторизации или парсинг
бросает исключение — запрос отклоняется или проходит дальше? Безопасно только
первое. `catch` с `continue` вокруг проверки прав — дыра.

**Посмотри на стыки.** Два компонента, каждый по отдельности правильный,
часто ломаются вместе: один нормализует путь, другой нет; один считает в
копейках, другой в рублях; фронт проверяет лимит, бэк — нет; парсер URL в
проверке и в HTTP-клиенте понимают строку по-разному.

**Посмотри на то, что «никто не вызовет».** Отладочные эндпоинты, тестовые
команды бота, флаги вроде `--insecure`, старые версии API, админка без
авторизации «потому что она на localhost».

## 2. Ввод и парсинг

- Проверяй по белому списку, а не по чёрному: допустимые символы, диапазон,
  длина, enum. Отрезать «опасное» почти никогда не получается полностью.
- Валидируй после декодирования и нормализации, а не до: иначе `%2e%2e`,
  двойное кодирование и юникод проходят мимо.
- Ограничивай длину до парсинга, а не после.
- Числа из внешних данных проверяй на диапазон перед арифметикой и
  выделением памяти по ним.
- Регулярки на пользовательском вводе — без вложенных квантификаторов
  (`(a+)+`), иначе ReDoS. Или с ограничением длины входа.
- Десериализация чужих данных — только в данные, не в объекты: никаких
  `pickle`, `yaml.load` без safe-loader, `BinaryFormatter`, Java
  `ObjectInputStream`, `eval` на JSON.
- XML от чужих — с отключёнными внешними сущностями и DTD.
- Шаблонизаторы: пользовательская строка — это данные в шаблоне, а не шаблон.

## 3. Файлы и пути

- Путь из внешних данных: собирай относительно базового каталога, резолвь
  (`realpath`, `canonicalize`, `filepath.Clean` + проверка префикса) и
  проверяй, что результат внутри базы. Учитывай абсолютные пути, `..`,
  симлинки, `\` на Windows, имена `CON`, `NUL`, двоеточия и ADS.
- Архивы: каждое имя внутри — враждебный путь (zip slip). Плюс лимит на
  суммарный распакованный размер и число файлов (zip bomb). Симлинки и
  хардлинки внутри tar — отдельно запрещай или резолвь.
- TOCTOU: «проверил, что файла нет, потом создал» — гонка. Создавай атомарно
  (`O_CREAT|O_EXCL`, `O_NOFOLLOW`), работай через открытый дескриптор, а не
  повторно по пути.
- Запись важных файлов — во временный файл в том же каталоге, `fsync`,
  потом `rename`. Иначе при падении остаётся полуфайл.
- Временные файлы — через `mkstemp`/`tempfile`/`os.CreateTemp`, не
  предсказуемое имя в `/tmp`.
- Права: конфиги с секретами — `0600`, каталоги — `0700`. Никаких `0777`.
  Учитывай umask и то, что файл существовал раньше с другими правами.
- Загрузки от пользователя: не доверяй расширению и `Content-Type`, храни
  вне веб-корня, имя генерируй сам.

## 4. Процессы и shell

- Запуск команд — списком аргументов без shell: `subprocess.run([...])`,
  `exec.Command(name, args...)`, `Command::new`. Никакого `shell=True`,
  `system()`, `popen()` со склеенной строкой.
- Даже без shell пользовательский аргумент может начинаться с `-` и стать
  флагом (`--output=/etc/...`, `-oProxyCommand=`). Ставь `--` перед
  позиционными аргументами или проверяй первый символ.
- Полный путь к бинарнику или контроль `PATH`, если программа запускается с
  повышенными правами или из чужого окружения.
- Не передавай секреты аргументами командной строки — их видно в `ps` и
  `/proc`. Через stdin, файл с правами 0600 или env (и то осторожно).
- В bash: кавычки вокруг всех переменных, `set -euo pipefail`, никакого
  `eval` с внешними данными.

## 5. Сеть и исходящие запросы

- TLS-проверка включена всегда. `verify=False`, `InsecureSkipVerify`,
  `rejectUnauthorized: false`, свой `TrustManager`, принимающий всё, — только
  если пользователь явно попросил и понимает зачем.
- SSRF: если сервер ходит по URL от пользователя, проверяй хост после
  резолва DNS, а не строку. Запрещай приватные, loopback, link-local
  (`169.254.169.254`), IPv6-аналоги и маппинг `::ffff:127.0.0.1`, а также
  десятичные и восьмеричные формы IP. Отключи редиректы или проверяй каждый.
  Держи соединение на тот IP, который проверил (DNS rebinding).
- Таймауты на всё: connect, read, общий. Лимит на размер ответа.
- Ответ чужого API — тоже ввод. Не вставляй его в HTML, SQL или путь без
  проверки.
- Слушай на `127.0.0.1`, а не на `0.0.0.0`, если сервис не должен быть
  доступен снаружи. Локальный сервис без авторизации доступен любой
  программе на машине и иногда браузеру через DNS rebinding.
- Прокси и обходы блокировок: не превращай свой прокси в открытый — доступ
  только с нужных адресов или по ключу; не логируй, куда ходят клиенты.

## 6. Веб и API

- SQL — только параметризованные запросы. Имена таблиц и колонок из ввода —
  только через белый список.
- XSS: экранируй при выводе по контексту (HTML, атрибут, JS, URL). В JS —
  `textContent`, а не `innerHTML`. `href` из ввода — проверяй схему
  (`javascript:`).
- IDOR: каждый запрос к объекту проверяет, что объект принадлежит
  текущему пользователю. id в URL или теле — не доказательство прав.
- Mass assignment: не мапь тело запроса целиком на модель. Явно бери
  разрешённые поля — иначе кто-то пришлёт `"is_admin": true` или
  `"price": 1`.
- Цена, скидка, итог, роль, статус заказа — всегда считаются на сервере.
  Клиент присылает только id товара и количество.
- CSRF: для cookie-сессий — токен или `SameSite`. Изменение состояния
  только не-GET запросами.
- CORS: не отражай любой `Origin` с `credentials: true`.
- Открытые редиректы: `?next=` — только относительный путь или белый
  список.
- Вебхуки (VK Callback, Telegram, платёжки): проверяй подпись или секрет
  до любой обработки, сравнивай за постоянное время, отбрасывай повторы
  по id события и старые по времени.
- Мини-приложения VK и Telegram: параметры запуска проверяй по подписи на
  сервере. `user_id` из фронта без подписи — подделывается за минуту.
- Rate limit на логин, отправку кодов, создание заказов, дорогие
  эндпоинты.
- Заголовки и логи: перевод строки во вводе — инъекция заголовка или
  поддельная строка лога.
- Ошибки наружу — без стектрейсов, путей и SQL.

## 7. Авторизация, сессии, токены

- Проверка прав — на сервере, на каждом действии, в одном месте, а не
  скрытием кнопки.
- Токены и коды — из криптостойкого генератора (`secrets`, `crypto/rand`,
  `OsRng`, `crypto.getRandomValues`, `RandomNumberGenerator`), достаточной
  длины. Не `random`, не `Math.random`, не время, не id.
- Пароли — только `argon2id`, `scrypt` или `bcrypt`. Не `md5`/`sha*` даже
  с солью.
- Сравнение секретов, подписей, токенов — за постоянное время
  (`hmac.compare_digest`, `subtle.ConstantTimeCompare`).
- JWT: фиксированный алгоритм на сервере, `none` запрещён, проверка `exp`,
  `aud`, `iss`. Секрет не в коде.
- Сессия меняется после логина и смены прав; выход реально её убивает на
  сервере.
- Одноразовые коды и ссылки: срок жизни, одна попытка использования,
  лимит попыток ввода.
- Сброс пароля и подтверждение почты не выдают, существует ли аккаунт.

## 8. Деньги, остатки и гонки

Самый частый класс логических дыр в магазинах, ботах автовыдачи и играх, и
его почти не бывает в типовых списках.

- «Прочитал баланс → проверил → записал» двумя запросами — двойная трата
  при параллельных запросах. Делай одной атомарной операцией
  (`UPDATE ... SET bal = bal - ? WHERE id = ? AND bal >= ?` и проверка
  числа строк), транзакцией с блокировкой или через мьютекс на ресурс, если
  процесс один.
- То же для остатков товара, промокодов, лимитов «одна заявка в день»,
  бонусов за приглашение.
- Идемпотентность: повтор одного и того же запроса (дабл-клик, ретрай
  сети, повторный вебхук) не должен давать второй заказ или вторую
  выдачу. Ключ идемпотентности или уникальный индекс на id события.
- Выдача товара — только после подтверждённой оплаты от платёжки, а не по
  сообщению покупателя «я оплатил» или по редиректу на success-страницу.
- Деньги — в целых минимальных единицах или decimal, не во float.
  Отрицательные количества и суммы запрещены явно.
- Округление и переполнение: что будет при количестве `2^31` или цене,
  умноженной на огромное число.
- Порядок шагов: сначала списать, потом выдать; при ошибке выдачи —
  вернуть или пометить для ручного разбора, но не терять событие.

## 9. Секреты и логи

- Секреты — из env, файла с правами 0600 или хранилища ОС. Не в коде, не в
  репо, не в примерах конфигов с реальными значениями. `.env` — в
  `.gitignore`.
- Не логируй токены, пароли, cookie, заголовок `Authorization`, полные
  тела запросов с персональными данными. Маскируй.
- Секрет не должен попадать в URL — он осядет в логах прокси и истории.
- Ошибки и паники могут вывести структуру с секретом: проверь, что
  `Debug`/`__repr__`/`toString` у конфига его не печатают.
- Секрет утёк в коммит — его нужно отозвать, а не только удалить из
  истории. Скажи об этом пользователю.

## 10. Криптография

- Не изобретай. Используй готовое высокоуровневое: libsodium/NaCl,
  `age`, AEAD (`AES-GCM`, `ChaCha20-Poly1305`) из стандартной библиотеки.
- Никакого ECB, никакого шифрования без аутентификации, никаких
  повторяющихся nonce с одним ключом.
- Подпись данных — HMAC, а не `hash(secret + data)`.
- Ключи из паролей — через KDF (`argon2`, `scrypt`, `pbkdf2` с большим
  числом итераций), не хешем.

## 11. Память и числа

- C/C++: никаких `gets`, `strcpy`, `strcat`, `sprintf` без размера.
  `snprintf`, проверка возвращаемого значения, явные размеры буферов.
- Размер из внешних данных умножается на размер элемента — проверь
  переполнение до `malloc`. Знаковые и беззнаковые в сравнениях длины.
- Use-after-free и двойное освобождение: RAII и умные указатели в C++,
  один владелец на ресурс.
- Строка формата всегда константа: `printf("%s", s)`, а не `printf(s)`.
- Rust: `unsafe` — только с понятным инвариантом рядом; индексы и
  арифметика с внешними числами — `checked_*`, `get()`; в релизе
  переполнение не паникует, а заворачивается.
- Go: гонки на map и общих структурах из горутин — мьютекс или канал;
  проверяй `-race`. Срезы от внешнего буфера держат его целиком.
- Java/Kotlin/C#: целочисленное переполнение тихое, проверяй размеры.

## 12. Ресурсы и отказ в обслуживании

- Лимиты на всё, что растёт от внешнего ввода: размер тела, число
  элементов, глубину вложенности JSON, число соединений, размер очереди,
  число файлов.
- Распаковка (gzip, zip, картинки) — лимит на результат, а не на вход.
- Кеши и мапы по ключу из ввода — с ограничением размера и вытеснением.
- Таймауты на чтение от клиента (slowloris), на внешние вызовы, на
  блокировки.
- Один медленный клиент или упавший обработчик не должен вешать весь
  сервис.

## 13. Десктоп и Linux

- Программа, которая работает от root или через `sudo`/polkit/setuid:
  минимум кода с правами, чистое окружение, полные пути, никаких записей в
  каталоги, доступные пользователю, без `O_NOFOLLOW`.
- Конфиги и плагины грузятся только из каталогов, которые принадлежат
  пользователю или root и не доступны на запись другим.
- Не выполняй файлы из текущего каталога неявно (Python ищет модули рядом
  со скриптом).
- D-Bus и сокеты: проверяй, кто звонит (uid отправителя, `SO_PEERCRED`),
  если метод делает что-то привилегированное.
- Устройства (`/dev/i2c-*` для DDC и т. п.): дай доступ группе через udev,
  а не запускай всё приложение от root.
- Автообновление — только по HTTPS и с проверкой подписи или хеша.
- Инсталляторы и скрипты dotfiles: не `curl | sh` с чужих адресов без
  проверки, не перезаписывай чужие файлы без бэкапа, не делай `chmod -R 777`.

## 14. Android

- Компоненты (`Activity`, `Service`, `Receiver`, `Provider`) —
  `exported="false"`, если не нужны снаружи. Экспортированные проверяют
  вызывающего и входящие `Intent`-extras как враждебный ввод.
- `PendingIntent` — `FLAG_IMMUTABLE` и явный компонент.
- `WebView`: без `addJavascriptInterface` для недоверенного контента, без
  `setAllowFileAccess`, без загрузки произвольных URL из intent.
- Cleartext-трафик запрещён (`networkSecurityConfig`), кроме явно нужных
  локальных адресов.
- Секреты — в Android Keystore, не в `SharedPreferences` и не в коде APK:
  APK декомпилируется.
- Логи `Log.d` с данными пользователя — убрать из релиза.
- Локальный сервер или прокси на устройстве слушает только loopback, и
  желательно с токеном: другие приложения на телефоне тоже могут к нему
  подключиться.
- Нативный код через JNI — всё из раздела 11.

## 15. Клиент-сервер в играх и модах

Сервер мода (Forge, Fabric, плагины) — та же граница доверия, что у
веб-сервера. Модифицированный клиент шлёт любые пакеты.

- Каждый пакет от клиента на сервере проверяет: существует ли сущность,
  принадлежит ли игроку, находится ли игрок рядом (расстояние), есть ли у
  него предмет, не на кулдауне ли действие, допустимы ли значения (скорость,
  угол, урон, координаты в пределах мира).
- Урон, взрывы, выдача предметов, телепорт, спавн сущностей — решает
  сервер. Клиент присылает намерение («нажал выстрел»), а не результат
  («нанёс 1000 урона по entity 42»).
- Ограничивай частоту пакетов от одного игрока.
- Обработчики пакетов выполняй в главном потоке сервера
  (`enqueueWork`), иначе гонки с миром.
- Строки и NBT из пакетов — лимит длины и глубины.
- Не загружай классы, ресурсы и скрипты по имени из пакета.

## 16. Зависимости и сборка

- Ставь только нужные зависимости, с проверенным именем (тайпосквоттинг
  `reqeusts`, `colourama`) и зафиксированной версией (lock-файл).
- Не подключай скрипты и библиотеки с CDN без `integrity`.
- CI: секреты не в логах, пулл-реквесты из форков не получают секреты.
- Docker: не от root, без секретов в слоях, минимальный базовый образ.

## 17. Ловушки по языкам

- **Python:** `eval`/`exec`, `pickle`, `yaml.load`, `shell=True`,
  `tarfile.extractall` без фильтра, `tempfile.mktemp`, `assert` для проверок
  (выключается флагом `-O`), `random` для токенов, f-строки в SQL.
- **Go:** `InsecureSkipVerify`, `http.Get` без таймаута (у дефолтного
  клиента его нет), `filepath.Join` не защищает от `..`, гонки map,
  `text/template` вместо `html/template` для HTML, `math/rand` для токенов.
- **Rust:** `unsafe` без инварианта, `as` молча обрезает числа,
  переполнение в релизе, `std::process::Command` с `sh -c`,
  `Path::join` с абсолютным путём заменяет базу.
- **C/C++:** раздел 11, плюс `system()`, `tmpnam`, `rand()` для секретов,
  неинициализированная память в ответе по сети.
- **JS/TS:** `innerHTML`, `eval`, `new Function`, prototype pollution через
  слияние объектов из JSON (`__proto__`, `constructor`), `child_process.exec`,
  `==` в проверках, регулярки без якорей при проверке origin или URL.
- **C#:** `BinaryFormatter`, `Process.Start` с `UseShellExecute` и строкой,
  `SqlCommand` со склейкой, `Random` для токенов.
- **Java/Kotlin:** десериализация, XXE в стандартных парсерах, `Runtime.exec`
  со строкой, логирование ввода в старых log4j-подобных библиотеках.
- **Dart/Flutter:** секреты в коде приложения, `http` без проверки
  сертификата через `badCertificateCallback: (_, __, ___) => true`,
  данные в `SharedPreferences` вместо `flutter_secure_storage`.
- **Bash:** переменные без кавычек, `eval`, `rm -rf "$dir/"` с пустой
  переменной (`${dir:?}`), парсинг `ls`, временные файлы с `$$`.
