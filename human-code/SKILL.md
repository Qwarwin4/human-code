# Human code

Код от ИИ узнаётся с полувзгляда, и не потому что он плохой — он *одинаковый*. Каждая функция с докстрингом, каждая строка с комментарием, `try/except` вокруг всего, `print("✅ Done!")`, разделители `# ===== Helpers =====`. Живой разработчик так не пишет: у него нет времени объяснять очевидное, он доверяет своему же коду и пишет под конкретную задачу, а не под абстрактного читателя-новичка.

Цель скилла — код, который выглядит как работа уверенного разработчика средней-высокой квалификации: точный, идиоматичный, без воды. Это не про небрежность. Опечатки, баги и мусор специально не добавляются — «человечность» достигается тем, чего в коде *нет*.

## Порядок работы

1. **Сначала посмотри на существующий код.** Если правишь проект — его стиль главнее всего, что написано ниже. Имена, отступы, способ обработки ошибок, наличие/отсутствие комментариев, язык комментариев — копируй как есть. Чужеродный кусок в чужом стиле палится сильнее всего.
2. **Напиши рабочий код.** Корректность на первом месте.
3. **Пройдись по нему чек-листом ниже** и вырежи всё лишнее. Обычно после этого код становится на 20–40% короче.
4. Для языковых тонкостей открой `references/languages.md` (нужный раздел). Если сомневаешься, как выглядит «до/после», — `references/examples.md`.
5. Если пишешь файлы на диск, можно прогнать `python scripts/smell.py <файлы>` — найдёт механически ловимые признаки (эмодзи, разделители, шаблонные докстринги, «Example usage»). Это подсказка, не приговор.

## Что выдаёт ИИ — и что делать вместо этого

### Комментарии

Человек комментирует *почему*, а не *что*, и делает это редко — там, где без комментария следующий читатель споткнётся.

- Убери комментарии, пересказывающие код: `# increment counter`, `// loop through users`, `# return the result`.
- Убери докстринги на тривиальных и приватных функциях. Шаблон `Args: / Returns: / Raises:` — только для публичного API библиотеки, и то если в проекте так принято.
- Убери шапки модулей вида «This module provides utilities for...».
- Никаких разделителей: `# ====`, `// ------ Helpers ------`, `#region` без нужды.
- Никаких следов диалога: `# Fixed: ...`, `# Changed to use X instead of Y`, `# Updated per request`, `# New implementation`. Код не знает о переписке.
- Никаких заглушек-оправданий: `# In a real application you would...`, `# TODO: add proper error handling`, `# Your code here`.
- Оставь комментарий, если он несёт информацию, которой нет в коде: обходной путь бага, ссылку на issue, неочевидный инвариант, причину странного числа. Пиши коротко, строчными, без точки в конце, как заметку для себя: `# xdg-open виснет без этого на kde`.

### Имена

Длина имени пропорциональна области видимости. Счётчик в трёхстрочном цикле — `i`, буфер — `buf`, конфиг — `cfg`, соединение — `conn`, ошибка — `err`/`e`. Длинное описательное имя — для того, что живёт долго и используется далеко от места объявления.

- Не `user_input_validation_result`, а `ok` или `valid`.
- Не `current_index_in_list`, а `i`.
- Избегай пустых суффиксов `Manager`, `Handler`, `Helper`, `Util`, `Processor`, `Service` там, где класс просто что-то делает — назови по сути (`Player`, `Cache`, `Queue`).
- Избегай безликого `data`, `result`, `process_data()`, `handle()` — если уж короткое, то конкретное: `rows`, `resp`, `parse()`.
- Сокращения, общепринятые в домене и языке, — норма: `ctx`, `req`, `res`, `msg`, `pkt`, `fd`, `addr`, `idx`, `tmp`, `src`, `dst`, `n`.

### Структура и абстракции

ИИ проектирует под воображаемое расширение. Человек пишет под текущую задачу и выносит код, когда он реально повторился.

- Не создавай класс с одним методом — это функция.
- Не заводи фабрики, стратегии, интерфейсы и dataclass-конфиги для двух-трёх значений, если нет второй реализации.
- Не дроби на функции по 3 строки, которые вызываются один раз. Хелпер оправдан, если он переиспользуется или его имя объясняет то, что иначе непонятно.
- Не выноси каждое число в `SCREAMING_CONSTANT`. Константа — если значение используется в нескольких местах или его смысл неочевиден.
- Не добавляй `argparse`, `logging.basicConfig`, `main()` с `if __name__ == "__main__"` в скрипт на 20 строк, если об этом не просили. Но в нормальной утилите — да, это обычное дело.
- Код не обязан быть симметричным. Если одна ветка — одна строка, а другая — десять, это нормально.
- Ранний `return`/`continue` вместо вложенности; без `else` после `return`.

### Обработка ошибок

- Проверяй на границах (ввод пользователя, сеть, файлы, внешние API), а своим же внутренним функциям доверяй.
- Не оборачивай всё в `try/except Exception` с логированием и `return None`. Ловить нужно то, что умеешь обработать; остальное пусть падает или поднимается выше.
- Не проверяй на `None`/`null` то, что не может быть `None`. Не делай `isinstance`-проверок аргументов внутри своего кода.
- Сообщения об ошибках — короткие, строчные, без точки и восклицаний: `"bad config: %v"`, `"no such device"`, `"failed to open {path}"`. Не «An error occurred while attempting to open the file. Please check...».

### Вывод и логи

- Никаких эмодзи в `print`/логах/CLI: ни `✅`, ни `🚀`, ни `❌`. Только если это часть задуманного UI и пользователь этого хочет.
- Не логируй каждый шаг (`Starting...`, `Processing item 3...`, `Done!`). Человек выводит то, что реально нужно видеть.
- Не печатай баннеры и рамки из `=` в консольных утилитах без запроса.

### Местные обычаи языка

У каждого языка свои устоявшиеся привычки, которые его сообщество соблюдает почти без исключений: регистр имён, где ставить подчёркивания, как писать аббревиатуры, какие префиксы и суффиксы приняты, как называть файлы и модули. Живой разработчик на этом языке делает так на автомате, а смешение обычаев разных языков — один из самых явных признаков чужака: `camelCase` в Rust, `SCREAMING_CASE` у констант в Dart, `get_` у геттеров в Go, `I`-префикс у интерфейсов в TypeScript.

- Перед тем как писать на языке, вспомни его обычаи и следуй им. Краткая шпаргалка по каждому языку — в начале его раздела в `references/languages.md`.
- Если проект отступает от обычаев языка — следуй проекту.
- Не переноси привычки одного языка в другой, даже если в соседнем файле на другом языке так принято.

### Длина строки

Общее правило почти для всех: строка не длиннее ~80 символов. Длинные строки читаются хуже, плохо смотрятся в diff и в разделённом редакторе, а у ИИ это частый признак — цепочки вызовов и условия в одну строку на полэкрана.

- Если у проекта или у форматтера языка свой лимит — он главнее.
- Переноси по смыслу: после запятой в аргументах, перед оператором в длинном условии, по звеньям цепочки вызовов. Иногда лучше вынести кусок в переменную с коротким понятным именем, чем переносить.
- Длинные строковые литералы, URL и пути можно оставить как есть — резать их хуже.

### Типы и синтаксис

- Аннотации типов — там, где они приняты в языке и проекте (сигнатуры), а не на каждой локальной переменной.
- Используй идиомы языка: генераторы и comprehensions в Python, `?` в Rust, `if err != nil` в Go, `auto` и range-for в C++, `?.`/`??` в TS/C#/Dart.
- Не пиши `if x == True`, `if len(lst) > 0`, `return True if cond else False`.
- Форматирование — стандартное для языка (gofmt, rustfmt, black/ruff, clang-format по проекту), без выравнивания пробелами «для красоты».

### Что вокруг кода

- Не добавляй блоки `# Example usage:` и демо-вызовы в конец модуля.
- Не пиши README, тесты, конфиги, которых не просили.
- В ответе пользователю не пересказывай код построчно. Пара предложений о том, что важно (неочевидное решение, что ещё не сделано) — достаточно.
- Коммит-сообщения: коротко, строчными, в повелительном наклонении, без эмодзи и conventional-префиксов, если репозиторий их не использует: `fix crash on empty playlist`, `add ddc retry`.

## Чего не делать во имя «человечности»

- Не вставляй намеренные опечатки, мёртвый код, закомментированные куски, рандомные несоответствия стиля — это не человечность, а мусор.
- Не убирай реально нужную обработку ошибок и валидацию входа.
- Не сокращай имена публичного API до нечитаемости: `get_ctx()` — норм, `gctx()` — нет.
- Если пользователь или проект явно хотят докстринги, логи, типы на всём — их правила главнее.

## Быстрая самопроверка перед отдачей

- Есть ли комментарий, который можно удалить без потери информации? Удали.
- Есть ли функция/класс, вызываемые один раз и ничего не проясняющие? Встрой.
- Есть ли `try`, `if x is None`, `isinstance`, которые никогда не сработают? Убери.
- Есть ли имя длиннее трёх слов у переменной с областью в несколько строк? Сократи.
- Соответствуют ли имена обычаям языка (регистр, подчёркивания, аббревиатуры)? Строки укладываются в ~80 символов?
- Есть ли эмодзи, разделители, «Example usage», «In a real app»? Убери.
- Похож ли код на соседние файлы проекта? Если нет — подгони.
